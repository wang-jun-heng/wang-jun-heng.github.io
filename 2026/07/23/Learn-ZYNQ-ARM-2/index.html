8 自定义IP核

前面学过AXI GPIO，这个实验使用的是赛灵斯官方的IP核去实现的功能。赛灵斯官方提供了很多的IP核，比如AXI DMI、AXI VDMI等等，但这些IP核往往是针对通用的使用场景，并不能事完全适应各种情况，那这时候就需要程序员去自己编写Verilog代码，封装成自己的IP核加入到Block Design里面，这个就叫自定义的IP核。

ZYNQ包含PS和PL，PS跟PL是怎么通信的呢——通过AXI接口通信对吧，所以说自己在实现功能的时候，难免是需要写AXI的接口协议，而这个Vivado软件提供了一种封装IP核的形式，它可以封装带AXI接口的一个IP核，简单说程序员只专注实现核心功能，利用AXI进行PS和PL通信部分软件能自动生成。

8.1 自定义IP核概述

自定义IP核是指在Vivado软件环境下，借助创建和封装IP向导的功能，把用户按照特定需求所设计的硬件模块封装成IP核的形式。

9 UART外设

9.1 UART控制器介绍

9.1.1 UART控制器概念

UART控制器是一个全双工异步收发控制器，用于实现设备之间的串行通信，ZYNQ/MPSoC内部包含两个UART控制器——UART0和UART1。

9.1.2 UART控制器特性

  • 波特率可调
    • 支持可编程的波特率发生器，允许用户根据需要设置通信速率
  • 数据位/校验位/停止位可配置
    • 数据位可配置为6bit、7bit和8bit
    • 校验位可配置为奇(Odd)、偶(Even)、空格(Space)、标记(Mark)和无校验
    • 停止位可配置为1bit、1.5bit和2bit
  • 错误检测
    • 支持奇偶校验错误、帧错误和溢出错误检测
  • 环回模式
    • 支持正常模式、自动回音模式、本地环回模式和远程环回模式
  • 中断支持
    • 支持多种状态触发中断，如接收FIFO达到阈值、接收超时等

9.1.3 UART系统视图

UART系统视图主要展示它的端口以及主要功能模块。后面还会有一个系统框图，更详细地展开它内部的功能。

首先，要支持中断功能，那么肯定会有中断请求id，也即图中左上角IRQ ID（注意，再次强调中断请求ID是用来区分中断来自于哪个外设）。因为ZYNQ有2个UART，所以针对这个UART的控制器是有两个中断ID的59和82。

⚠️ 不同外设的中断ID也不用死记硬背，因为在编写代码的时候，这个软件里面都帮我们把不同外设的中断ID给使用个宏定义的方式给定义好了，直接把定义好的宏定义参数拿来用就行了。

然后，还需要提供参考的复位UART REF_RST和时钟REF_CLK。

接着，一个比较关键的接口就是图中的APB从机接口，这个APB是一个高级外设接口，是AMBA接口总线的一部分（像前面学习的AXI接口呢，也是属于AMBA接口协议的一部分）。APB主要是用在一些低速的通信上面，比如对一些寄存器进行配置等。

中间左侧方框是UART控制器内部的一个视图，它包含UART接口的控制器UART Interface Controller和控制状态寄存器Control And Status Registers，对UART进行配置或者收发数据都是通过操作寄存器来实现的。

中间右侧方框有一个MIO-EMIO的路由MIO-EMIO Routing，也就是说你可以把UART的控制器的引脚连接到MIO引脚，也可以通过EMIO来连接到PL端的引脚。

🚦注意，从上图可以发现，它在连接到MIO或者是EMIO的时候会有一些差异：

  • 当连接到MIO引脚的时候呢可以发现它只有Tx和Rx两个引脚
  • 当通过EMIO连接到PL端引脚的时候，除了Tx和Rx之外，它还有CTSN、DCDN、DSRN等
    • CTSN,DCDN,DSRN,RIN,DTRN,RTSN这些引脚有一个专门的名词叫——modem control——一个调制解调器的控制，用于对整个串口的硬件数据流进行控制。它本质上是用来确保整个数据传输的可靠性和稳定性的，由于它会占用非常多的引脚，所以说这几个引脚一般用的也不多。只有在对整个通信要求稳定性更高的场景，比方说一些医疗设备或者是工业自动化等场景中使用。

9.1.4.1 TxFIFO简介

详细看一下发送端的FIFO，因为这个FIFO比较关键。TxFIFO中存储从APB接口写入的数据，直到它被Transmitter读出并加载至移位寄存器中；用户通过写TxFIFO寄存器将数据写入TxFIFO中：

它是个FIFO，也即是一个先入先出的缓存器，所以说它可以产生一些标志位，这些标志位可以让它产生中断，如上图所示：

  • 满信号Full Interrupt[TFUL——当FIFO被写满时会置此标志位，并且可以产生中断。
  • 触发阈值Full Interrupt[TFUL]——比方说把FIFO阈值设置成5，那么FIFO中存储的数据达到5个数据之后，就会置此标志位，并且可以产生中断。
  • 空信号Empty Interrupt[TEMPTY]——当FIFO中是空的时会置此标志位，并且可以产生中断。
  • 将满信号Nearly Full Interrupt[TNFUL]——当FIFO存储的数据快要填满整个FIFO时会置此标志位，并且可以产生中断。
  • 溢出信号Overflow Interrupt[TOVR]——当FIFO写满之后，还要继续写数据，那么它会产生溢出中断。

9.1.4.2 RxFIFO简介

这个接收端的FIFO其实跟TxFIFO比较类似，就是一个反的过程：RxFIFO中存储从移位寄存器接收的数据，直到它被APB接口读出，用户通过读RxFIFO寄存器将数据从RxFIFO中读出；

9.1.4.3 UART的四种模式

下面来看一下UART的四种模式：

第一种是正常模式，就是一个正常的串口数据收发。一般正常操作就使用这种模式。

第二种是Automatic Echo Mode，给它翻译成自动回音模式，从示意图可以发现，对于接收端来说是正常的，但是发送端是断开的，所以说发送端实际上是没有用的，它所接收的数据一方面连写到RxFIFO中，另外一方面它又把它通过发送端口发出去了。可用于排查串口接收问题。

第三种是Local Loopback Mode，给它翻译成本地环回的模式，从示意图可以发现，它的发送器直接连接到接收器，并没有跟外部的引脚连接。那这种模式应用在什么场景呢？比方说大家的板卡没有USB串口，那么你就没有硬件来去调试这个接口对吧，但又想确认这个程序有没有问题，那只能是进行一个本地的还回，相当于发什么又还回过来了，从而来验证程序是否正确。

第四种是Remote Loopback Mode，给它翻译远程环回模式，它的接收端直接连接到发送端，并没有跟本地进行一个连接，全是是断开的。

10 定时器外设

定时器顾名思义就是实现定时计时的功能，ZYNQ的PS端的定时器跟STM32的定时器其实实现的功能都是一样的，主要是一个计时的功能。除此之外，它还可以控制某个引脚输出PWM波；然后还可以采集外部引脚输入的信号，比如说来计算出外部输入信号的脉宽。

当然对于ZYNQ来说，我们使用PS端的定时器主要还是使用它计时的功能，像对引脚输出PWM波或者是计算外面输入信号的脉宽的话呢，一般可以使用PL端来实现（这种对PL端来说是比较简单的）。这个时候有些小伙伴可能有疑问了，我们前面比方说对led灯的控制，每隔一秒钟控制它亮灭不是可以直接用sleep语句吗，用sleep语句就可以实现延迟了，为什么还要用定时器呢？其实sleep语句本质上还是在CPU里做延迟，CPU在那里傻等着，等到延迟一秒钟之后，它继续执行后面的操作，在这个等待过程当中CPU什么也干不了，所以说这会严重降低CPU的执行效率。

而使用定时器它不依赖于CPU，它可以自己进行定时，当定时完成之后，比方说产生一个中断告诉CPU，这样的话CPU知道延迟时间够了，然后可以执行一个设定好的操作，而不用CPU一直在那里等待，这是定时器最关键的一个功能。

10.1 定时器简介

本小节主要是想带领着大家来看一下赛灵思官方手册，来看一下官方手册是怎么介绍这个定时器的。这样以后自己在学习一个新的外设的时候，可以知道怎么去学习一个新的外设。

打开官方文档——ug585-Zynq-7000-TRM.pdf（如果是NPSOC的板卡就查看ug1085）。然后找到定时器所在的第八章来看一下：

这里说每一个cortex a9处理器（因为像7020、7010等它们是包含双核的，所以说每一个a9处理器）它都有自己的私有32位定时器，还有一个32位看门狗定时器。然后这两个a9处理器共享一个64位的定时器，这些定时器的时钟是来自于1/2的CPU时钟频率（对于ZYNQ来说，一般CPU时钟频率是666.666MHz，则1/2就是333.333MHz）。

接着，从系统层面来说，还有一个24位的看门狗定时器和两个16位的三路定时器（triple就是三路的意思，也叫TTC定时器）。（后面的内容就不翻译了……）

XScuTimer_CfgInitialize 是 Xilinx（现 AMD）Zynq SoC 或 MicroBlaze 等嵌入式平台 standalone 驱动库中的一个核心初始化函数。它的主要作用是‌将硬件的静态配置信息与软件运行时实例进行绑定和初始化‌。

在 STM32 开发中没有遇到过完全对应的单一函数，是因为 STM32 的标准库（Standard Peripheral Library）或 HAL 库的设计哲学与 Xilinx 的驱动架构不同。以下是详细对比和原理解析：

  1. XScuTimer_CfgInitialize 的具体作用

在 Xilinx 的驱动模型中，外设初始化通常分为两个步骤：‌查找配置‌ 和 ‌初始化实例‌。XScuTimer_CfgInitialize 负责第二步，其内部主要完成以下工作：

① 绑定硬件地址‌：它将查找到的硬件基地址（Base Address，例如 0xF8F00600 用于私有定时器）写入到软件实例结构体 (XScuTimer *InstancePtr) 中。这样，后续的 API 调用（如 XScuTimer_Start）才知道去操作哪一块内存寄存器。
② 重置外设状态‌：它通常会调用底层的复位逻辑，将定时器控制器恢复到已知的默认状态（例如：停止计数、禁用中断、清除标志位、禁用自动重载等）。这确保了无论之前硬件处于什么状态，初始化后都是干净的。
③ 标记实例为“就绪”‌：它在软件结构体中设置一个标志位（如 IsReady），表明该实例已经过初始化，可以安全使用。后续的其他驱动函数会检查这个标志，防止未初始化就使用导致错误。

  1. 为什么 STM32 没有类似的函数？

STM32 的开发体验之所以感觉不同，主要是因为库函数的封装粒度和服务对象不同：

A. 设计架构差异
Xilinx (Standalone Drivers)‌：采用‌“配置结构体 + 实例结构体”‌分离的模式。
XScuTimer_Config：编译时生成的只读数据，包含硬件ID、基地址、中断ID等静态信息。
XScuTimer：运行时数据，包含当前状态、回调函数指针等。
XScuTimer_CfgInitialize 的作用就是桥接这两者。这种设计适合复杂的 SoC，其中外设数量多、地址可能动态变化或通过设备树传递。
STM32 (HAL/LL/Standard Lib)‌：采用‌“句柄/实例直接操作”‌或‌“寄存器宏直接操作”‌模式。
HAL 库‌：使用 HAL_TIM_Init(&htim)。这个函数确实存在，但它通常假设你已经手动填充了 htim.Instance（指向寄存器基址的指针）和 htim.Init（配置参数）。它更侧重于根据你填写的参数去配置寄存器，而不是从外部查找硬件地址。
标准库/寄存器编程‌：你直接操作 TIM2->CR1 = …。这里没有“初始化实例”的概念，因为基地址 TIM2 是一个固定的宏定义，编译器直接将其映射到内存地址。

关键点：‌ STM32 的 HAL_TIM_Init 其实承担了部分类似的角色，但它要求开发者事先知道并填好 htim.Instance = TIM2;。而 Xilinx 的 CfgInitialize 往往配合 LookupConfig 使用，旨在实现‌代码与具体硬件地址的解耦‌——如果你改变了 Vivado 工程中的定时器基地址，重新生成 BSP 后，代码无需修改，LookupConfig 会自动获取新地址。

  1. 总结
    XScuTimer_CfgInitialize 的核心价值‌：它是 Xilinx 驱动框架中‌“硬件抽象层”‌的关键一环，负责将编译时确定的硬件物理属性（基地址）注入到运行时软件对象中，并执行硬件复位。
    STM32 的对应物‌：最接近的是 HAL_TIM_Base_Init() 加上你手动赋值 htim.Instance 的过程。但在 STM32 简单应用中，由于硬件地址固定且已知，开发者往往直接通过宏访问寄存器，从而省略了“查找配置”和“绑定实例”这两个显式步骤，因此感觉上没有这样一个独立的“初始化配置”函数。

如果你正在从 STM32 转向 Zynq/MPSoC 开发，需要适应这种‌“先 Lookup 配置，再 CfgInitialize 绑定，最后配置功能”‌的三步走标准化驱动流程。这种流程在处理复杂 SoC 的多实例外设（如多个 UART、多个 Timer）时更具可维护性和移植性。

11 IIC外设

11.1 IIC和EEPROM简介

IIC控制器是指PS端的IO外设（前面学过其他的PS端的IO外设，比如GPIO、UART等都是PS端非常基础并且重要的外设）。通过学习IIC的控制器就可以对一些IIC的设备进行驱动和控制，像一些芯片的配置接口（比方说音频的配置接口）还有一些串行的ADC、DAC、还有RTC芯片，还有就是本次实验所学习的EEPROM，那么这些芯片都带有IIC接口。

注意，也可以使用GPIO来模拟IIC的时序来对这些带有IIC接口的芯片进行控制。但使用GPIO模拟的方式其通信的速率很难做高，另外一方面也会消耗CPU的资源。

11.1.1 IIC总线协议介绍

IIC：InterIntegrated Circuit，集成电路总线，是一种同步串行半双工通信总线。关于IIC，有些人说是IIC总线，有些人说是IIC协议，还有还有些人说是IIC总线协议，其实说法都对，因为IIC的标准既定义了它的接口也包含了它的协议。

总线：它其实是传输数据的一个通道（交通道路）
协议：它其实是传输数据的一个规则（交通规则）

下面来看一下IIC总线的结构图：

硬件结构‌：仅需两根线——串行数据线（SDA）和串行时钟线（SCL），均为双向开漏输出，需外接上拉电阻（常见4.7KΩ），空闲时总线保持高电平。

‌通信模式‌：支持一主多从和多主多从，同一时刻只有一个主机控制总线，每个从设备有唯一地址（7位或10位），主机通过地址寻址特定从机。

‌传输速率‌：标准模式100kbps，快速模式400kbps，高速模式可达3.4Mbps，总线负载电容上限400pF。

‌数据格式‌：以字节（8位）为单位传输，每字节后必须带应答位（ACK）；起始信号为SCL高电平期间SDA下降沿，停止信号为SCL高电平期间SDA上升沿。‌‌

通信流程：主机发起起始信号 → 发送从机地址（含读写位）→ 等待从机应答 → 传输数据（每字节后应答）→ 发送停止信号结束通信。‌‌

典型应用：常见于读取内存SPD信息、驱动LCD显示屏、连接各类传感器（如温湿度、加速度计）等场景，在STM32、ESP32等嵌入式开发中非常常用。‌‌

剩下的，比如IIC的协议时序等内容的介绍，参考我学STM32时候做的笔记：https://wang-jun-heng.github.io/2025/07/15/Learn-STM32-2/

11.1.2 AT24C64介绍

EEPROM是一种掉电后数据不丢失的储存器，常用来存储一些配置信息在系统重新上电时就可以加载。
AT24C64是一个64Kb的EEPROM存储器，使用IIC通信方式。AT24C64由256个页（Page）页组成，每页32个Byte。

注意，AT24C64每隔10ms才会刷新一次数据，并不是你写入进去里面就可以了，所以至少每隔10ms以上写一次数据。但是从AT24C64读数据是没有时间间隔要求的。

下面是AT24C64的原理图（A0、A1、A2可控制地址）

AT24C64是存储空间有8K个字节，所以需要13为才能表示其完整的存储空间。

‌AT24C64支持两种写操作模式：字节写（Byte Write）和页写（Page Write）‌，区别在于一次总线事务里写1个字节还是连续写最多32个字节。‌‌

  • 两种写操作模式对比
    • ‌字节写‌：一次事务写1个字节，帧结构为 START + 设备写地址 + 地址高字节 + 地址低字节 + 数据 + STOP。最简单可靠，但效率低，适合写单个参数或配置项。
    • ‌页写‌：一次事务连续写最多32字节，帧结构为 START + 设备写地址 + 地址高字节 + 地址低字节 + 数据0...数据N + STOP。效率高，批量写32字节只需1个写周期，比逐字节写快接近两个数量级。‌‌
  • 页写的关键限制
    • 页写有‌页边界回卷‌问题：AT24C64页大小为32字节，芯片内部地址计数器只对低5位自增，满后回卷到本页起始地址，不会自动进入下一页。‌‌
      • 从地址 0x1F 写2个字节，数据会写到 0x1F 和 0x00，而非 0x1F 和 0x20。
      • 从 0x001E 写3个字节，数据落在 0x001E、0x001F、0x0000，覆盖页首原有数据。‌‌
    • 因此驱动层必须做‌跨页拆分‌：每次写入不超过当前页剩余空间，写完一页等写周期结束再写下一页

发送了起始信号后，第一部分要先发送从机地址，第二部分发送访问的存储地址，第三部分发送写入的一字节数据。从机地址按硬件上EEPROM芯片的A2 A1 A0引脚接线来定义。此外，要注意10ms的时间间隔限制。

存储地址可以看到由13位组成，最左三位是无意义的位，因为按照上面所说，AT24C64可以存储8192个字节的数据，实际以0为起始的话就只有8191个数据，8191换算成二进制为00011111 11111111，可以看出刚好能由13位表示EEPROM内部数据的存储地址。

上图还可以知道AT24C64每页存放32个字节，那么就有8192/32 = 256页，页写入的时序如下图所示。

与按字节写入相比，页写入在第一个字节写完后再写了x个数据，因为AT24C64每页32个字节，所以这里的x = 3，也就是再写3byte后结束按页写入。

AT24C64的读操作主要有三种：当前地址读、随机读和顺序读‌，核心都是先定位内部地址指针，再通过I2C读时序取数据。读操作可以跨页，但不能跨块，且读的字节数越多出错概率越大，不建议一次性读太多数据。‌‌

  1. ‌当前地址读‌：直接发读地址帧（如0xA1），从上次操作留下的地址指针处开始读。若上次写或读停在地址0x0100，当前地址读即从0x0100取数。无需先发地址，最省事但位置不可控。‌‌

  2. ‌随机读‌：最常用，分两步：

    • ‌伪写阶段‌：发START → 发写地址（0xA0）→ 发16位内部地址高字节 → 发低字节，将内部地址指针设到目标位置。
    • ‌读阶段‌：发REPEATED START（不是STOP再START）→ 发读地址（0xA1）→ 读数据字节 → 发NACK → 发STOP。

    关键：两阶段间必须用重复起始条件，不能发STOP再发START，否则总线可能被其他主机抢占，导致地址错乱。‌‌

  3. ‌顺序读‌：随机读后不立即STOP，而是继续发ACK并读下一字节。每读一字节内部地址自动加1，可连续读任意长度。读完最后字节后发NACK再发STOP终止。‌‌

读时序流程（随机读为例）

START → 发0xA0(写) → 等ACK → 发地址高字节 → 等ACK → 发地址低字节 → 等ACK→ REPEATED START → 发0xA1(读) → 等ACK → 读数据字节 → 发NACK → STOP

12 SD卡读写

12.1 SD卡介绍

SD：Secure Digital Card，称为安全数字卡（安全数码卡）。SD卡是在MMC（MultiMedia Card，多媒体卡）的基础上发展而来，增加了更高的安全性和更快的读写速度。SD卡的本质就是：Nand Flash+控制芯片。SD卡不支持XIP。

  • 📌 XIP的全称
    • XIP的标准全称是 ‌eXecute In Place‌，直译就是“就地执行”，指代码可以直接在非易失性存储器里运行，不需要预先拷贝到RAM中加载执行。
  • 📌 QSPI FLASH对XIP的支持情况
    • ‌符合规范的QSPI NOR FLASH是支持XIP的‌，但有明确的前提条件：
      • 它需要MCU自带QSPI外设的内存映射模式支持，把外部Flash映射到CPU的统一编址空间里。
      • 只有支持随机字节寻址的NOR型QSPI Flash才能实现XIP，普通NAND型QSPI Flash不满足XIP的硬件要求。
      • 部分STM32高端系列（如F7、H7）的QSPI外设原生支持XIP，而STM32F1系列完全没有QSPI外设，自然无法外接QSPI Flash实现XIP。
  • 📌 为什么你会有“程序必须拷贝到内存运行”的印象
    • 这个认知是针对‌非XIP场景‌的：
      • 像Linux、Android这类资源充足的大型系统，内核和应用程序普遍会先从存储介质解压/拷贝到RAM再运行，以此获得更高的执行效率。
      • 普通SPI Flash没有内存映射机制，CPU无法直接从SPI外设按需取指，必须先把代码整段拷贝到RAM才能执行，否则根本无法运行。
      • XIP模式是“免搬运”，不是“零等待”，它的执行速度会比内部RAM慢，只是省去了拷贝的步骤，节省了RAM空间。
  • 📌 STM32F103C8T6的存储配置
    • 它‌不是没有内存，而是自带了20KB的SRAM‌，同时内置64KB的内部NOR Flash：
      • 它的程序直接烧录在内部NOR Flash里，本身就支持类似XIP的直接取指执行，不需要额外拷贝到RAM，这是Cortex-M内核MCU的常规设计。
      • 这颗芯片的SRAM仅用于存放全局变量、栈、堆、动态分配的内存，不用于存放主程序代码，所以你平时写的代码直接烧进内部Flash就能跑。
      • 它没有QSPI外设，也没有外部Flash的内存映射控制器，因此完全不支持外接QSPI Flash实现XIP功能。
      • STM32F103C8T6 内部集成的 Flash 本质上就是 ‌NOR Flash‌ 架构，它天然支持 ‌XIP（eXecute In Place，就地执行）‌。这意味着 CPU 可以直接从内部 Flash 中读取指令并执行，完全不需要像运行在外部 SPI Flash 或硬盘上的程序那样先拷贝到 RAM 中。
